# Retained chore history rollout

Apply `supabase/migrations/0007_retained_chore_history.sql` after 0006, before deploying this client. No rows are backfilled or deleted. Existing chores have a null end date; existing completions and legacy `progress.retired` values stay intact. The migration replaces the object cascade with a composite owner FK that detaches only `object_id`.

`Chore.archivedOn` maps to `chores.archived_on`, an exclusive local calendar end date. `selectHome().chores` includes archives. Use all chores for history, rewards and restoration, and `choreActiveOn` for obligations. Archived tasks cannot be reopened or edited by stale upserts. A first archive keeps the server's current task metadata and schedule. Unsynced edits concurrent with archival can therefore lose to the authoritative server schedule. Already recorded completions are immutable to updates; explicit completion deletion for Undo remains supported.

Furniture removal carries optional `removal: { archivedOn, keepChores }` on the queued delete. `Remote.remove` forwards it to `remove_objects(uuid[], date, boolean)`. This invoker RPC locks each visible object, detaches all its tasks, optionally archives them, and deletes the object in one transaction. It handles tasks unknown to the requesting device. Composite owner FKs and existing RLS remain in force. Tasks created offline are first queued as detached upserts so deleting their never-synced object cannot strand their completions.

Old clients and old offline outboxes may still issue hard DELETEs. After this migration, chore DELETEs archive in a trigger; furniture DELETEs archive/detach attached tasks before removal. These legacy requests lack the original local removal date, so they use the server calendar date at sync time, clamped to creation. Completion writes arriving before or after archival retain credit. Old clients remain unaware of archives and may display them as active tasks or accept later completions. Require an app reload/update for correct obligations and historical displays; do not advertise full old-client UI compatibility.

Whole-home removal and `delete_my_account()` still physically erase all owned rows. The deletion trigger checks parent existence, with a narrowly scoped definer function and empty search path, to permit those cascades. Trigger functions are not directly callable by authenticated or anonymous users. Only the object-removal RPC is exposed to authenticated users.

Legacy retired counts provide a count-only fallback for chores already destroyed before deployment. A retained chore uses its completion rows, ignoring its old bank, so they cannot double count. The migration cannot reconstruct completion dates or schedules already deleted by the old schema, or unsynced facts an old client already discarded locally. Recover those only from a separate backup if one exists. Do not invent dates from cached totals.

Run `npm test -- supabase/migrations.test.ts src/data/retainedHistory.test.ts src/data/remote.test.ts` before rollout. The PGlite suite applies all migrations with Supabase-like roles/RLS and exercises actual SQL cascades, both arrival orders of the completion/delete race, tenant isolation, legacy deletes, upgrade preservation and full account deletion. It does not emulate the hosted Auth service or parallel PostgREST network requests. A staging smoke check should repeat two-device removal and account deletion before release.

Rollback the client only while retaining this migration's protections. Dropping archive metadata or restoring destructive cascades would reintroduce data loss. Nothing in this PR deploys the migration.
